Building a Strava Data Pipeline from Scratch

Syncing athlete data from Strava sounds simple. OAuth, webhooks, a few API calls, done. Then you actually build it, and you discover a series of edge cases that the documentation mentions only in passing — or not at all.

Here's what we learned building Omni Coach's Strava pipeline.

Start with the webhook, not the polling loop

The first version of our sync used a polling loop. Every 15 minutes, check for new activities. It worked fine for a handful of test users. It did not work fine when we added real coaches with real athlete rosters. The API rate limits hit fast, and the lag between an athlete finishing a run and a coach seeing the data was unacceptable.

Strava's webhook system is the right answer. When an athlete completes an activity, Strava sends you a push notification. You store the event, then process it asynchronously. The lag drops to seconds. The API calls become targeted rather than exploratory.

The catch: webhook subscriptions are per application, not per user. You get one endpoint for all your users' events. That endpoint needs to be fast, idempotent, and resilient to duplicate delivery — because Strava will retry if you don't respond with a 200 inside two seconds.

Token refresh is where things get interesting

Strava access tokens expire after six hours. Refresh tokens last longer, but they also rotate — each time you use a refresh token, you get a new one back. If two processes try to refresh the same token simultaneously, one of them will succeed and the other will get an invalid token error.

We solved this with a simple database lock: before refreshing, write a "refresh in progress" flag with a timestamp. If the flag is set and fresh, skip the refresh and wait. If the flag is stale (say, more than 30 seconds old), assume the previous refresh crashed and proceed anyway.

Handling revoked access gracefully

Athletes disconnect apps. Sometimes deliberately, sometimes by accident, sometimes because they switched phones and re-authorised without realising the old token was still in our system. Strava sends a deauthorisation event to your webhook endpoint, but you can't rely on always receiving it.

Our approach: treat every 401 as a potential permanent revocation. Log it, flag the athlete's connection as degraded, and surface it in the coach's dashboard. Don't silently swallow the error. Coaches need to know when data is missing, not discover it three weeks later during a review.

What we'd do differently

If I were starting over, I'd design the pipeline around eventual consistency from day one rather than bolting it on later. Assume every step can fail. Assume events will arrive out of order. Assume the same activity will be synced twice. Build the processing layer to be idempotent, and let the infrastructure worry about at-least-once delivery.

It's more upfront work. It's much less firefighting later.
